# Harness Engineering — เขียน test ให้ agent ไม่ใช่ให้โค้ดธรรมดา

Test ปกติตรวจว่า input A ให้ output B ตรงตามที่คาด แต่ agent ที่ทำงานจริงบน Discord ไม่ได้เจอแค่ input — มันเจอ **ความล้มเหลวที่มาแบบสุ่ม**: Codex ตอบ error, network timeout, quota หมดกลางทาง, Discord ปฏิเสธการส่งข้อความ

ถ้า test ไม่จำลองความล้มเหลวพวกนี้ ก็ไม่มีทางรู้เลยว่า agent จะรอด หรือจะค้างอยู่ในสถานะ `running` ตลอดกาล

## Failure harness ทำงานยังไง

`scripts/failure_harness.py` จำลองความล้มเหลวแบบออฟไลน์ทั้งหมด ด้วย fake Discord client และ SQLite ชั่วคราว ไม่ต้องพึ่งเครือข่ายจริงเลยสักครั้ง

```text
marker              atom-harness:failure:v1

Codex error (ไม่ใช่ capacity)   → ต้องจบเป็น failed
TimeoutError                    → ต้อง requeue เป็น pending พร้อม retry event
Discord delivery error          → ต้องจบเป็น failed ห้ามค้างเป็น running
ESP32 telemetry                 → ปิดในฮาร์เนสนี้ กันของฮาร์ดแวร์มาปนผลลัพธ์
```

จุดสำคัญคือ **"ต้องจบ" ไม่ใช่ "ควรจะจบ"** — งานทุกงานต้องมีสถานะสุดท้ายที่ชัดเจนเสมอ ไม่ว่าจะสำเร็จหรือพัง สถานะที่ค้างอยู่กลาง ๆ ตลอดกาลคือบั๊กในตัวมันเอง

## เมื่อ test coverage ธรรมดาไม่พอ ต้องไล่เข้าไปในฟังก์ชันที่ "ดูใหญ่เกินจะแตะ"

คนละงานแต่จิตวิญญาณเดียวกัน: `worker.py` มีฟังก์ชัน `build_prompt()` ยาว 200 บรรทัด เคยถูกมองข้ามเพราะ "ใหญ่เกินไป, branch เยอะเกินไป" จนกระทั่งวันหนึ่งไล่เขียน test จริงจังลงไป

```text
ก่อนหน้า   113 tests ผ่าน
หลังไล่    120 tests ผ่าน (+7 ใหม่เจาะ build_prompt())
repo รวม   340 passed, 1 failed (ตัวที่ fail ไม่เกี่ยวกับรอบนี้)
```

ไม่เจอบั๊กใหม่จากรอบนี้ — แต่นั่นก็เป็นข้อมูลที่มีค่า: ตอนนี้มี**หลักฐาน**ว่าฟังก์ชันที่ซับซ้อนที่สุดตัวหนึ่งในระบบทำงานถูกต้องตามที่ตั้งใจ ไม่ใช่แค่ "ดูน่าจะโอเค"

## บทเรียนที่ใช้ซ้ำได้

ไฟล์ที่ถูกแก้บ่อยที่สุดในประวัติ git คือไฟล์ที่ซับซ้อนทางธุรกิจมากที่สุด — และควรเป็นไฟล์ที่มี test มากที่สุด ไม่ใช่น้อยที่สุด เพราะ "มันใหญ่และซับซ้อน" ไม่ใช่เหตุผลให้ข้าม แต่เป็นเหตุผลที่ต้องเจาะลึกกว่าที่อื่น

Test ที่ดีที่สุดไม่ใช่ test ที่พิสูจน์ว่า happy path ทำงาน — คือ test ที่พิสูจน์ว่าระบบรู้ตัวว่าพังตอนไหน แล้วจบสถานะให้ถูกต้องเสมอ
