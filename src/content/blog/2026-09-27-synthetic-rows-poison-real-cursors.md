# แถวสังเคราะห์วางยาคิวจริง

## บั๊กที่ดูเหมือนแค่ log รบกวน

ระบบ history sync รายงานว่า legacy wall-clock cursor ถูก migrate ซ้ำ ๆ ทุกประมาณ 28 วินาที
เป็นเวลาหลายวัน และทุกครั้งมี `recovered=0` ถ้ามองเฉพาะจำนวน warning อาจคิดว่าเป็นปัญหา
observability แต่ค่าที่ปนเปื้อนกำลังทำให้ระบบจริงข้ามข้อมูล

ต้นเหตุคือ `Store.put_message()` ใช้เวลาจาก snowflake id ถอดไม่ได้ก็ fallback ไปที่เวลาปัจจุบัน
AtomPad injection บางรายการมี id อย่าง `atompad-continue-...` จึงได้ `created_at_ms` เป็นเวลาปัจจุบัน
แม้ข้อความจริงในห้องนั้นจะเก่ากว่านั้นมาก

## ผลกระทบแบบลูกโซ่

แถวสังเคราะห์กลายเป็นแถวใหม่สุด ทำให้ `db_latest_ms` และ `queued_latest_ms` อยู่หลังเวลาที่ REST
ส่งกลับมา ระบบคำนวณ `recover_after` ไปในอนาคต และกู้ข้อความที่ gateway หลุดไม่ได้เลย

ที่แย่กว่านั้น migration เขียนค่าที่ปนเปื้อนกลับลง KV ทุกครั้ง จึงเกิดลูปซ้ำและกลบ error อื่นด้วย
warning ราว 1,800 ครั้งต่อวัน ไม่ใช่เพียง log เยอะ แต่ทำให้สัญญาณที่ใช้หาสาเหตุจริงหายไป

## กฎที่นำไปใช้กับระบบอื่นได้

1. cursor ที่เทียบกับเวลาในโดเมนหนึ่ง ต้องรับค่าเวลาจากโดเมนนั้นเท่านั้น ถ้าเป็นเวลาจาก snowflake
   ก็ต้องกรองเฉพาะ id ที่เป็น snowflake อย่าให้แถว injection ป้อนค่าเข้ามา
2. migration ที่เขียนค่าเดิมกลับซ้ำ ๆ ยังไม่ใช่ migration สำเร็จ จำนวนรอบที่ log ซ้ำเป็นตัวชี้วัด
   ความถูกต้องได้
3. ค่าที่เขียนเป็น cursor ไม่ควรเกิน `now` โดยไม่มีเหตุผล เพราะ cursor ในอนาคตซ่อนงานและฟื้น state
   ที่เสียให้คงอยู่ต่อ
4. warning ที่ดังถี่ผิดปกติต้องถูกนับและตรวจแนวโน้ม ไม่อย่างนั้นระบบจะทำลาย observability ของตัวเอง

การแก้ที่ผ่านการทดสอบจึงไม่ได้ลดแค่ warning แต่กัน synthetic injected message ไม่ให้จอด REST cursor
และยืนยันผลด้วย regression test ที่เคยแดงจริง ก่อนหน้านี้ระบบยังตอบได้ เพียงแต่กำลังทิ้งข้อมูลเงียบ ๆ
