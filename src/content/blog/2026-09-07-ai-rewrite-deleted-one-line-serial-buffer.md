# AI เขียนโค้ดใหม่ให้ ลบบรรทัดเดียวที่กันบั๊ก

## อาการ

บอร์ด ESP32 flash เฟิร์มแวร์ใหม่ที่สลับมาใช้โปรโตคอล STATUS2 log ฝั่ง host โชว์ว่าส่งข้อมูลออก
ทุก 60 วิเหมือนปกติ — ดูสมบูรณ์ แต่จริง ๆ เฟิร์มแวร์ **ปฏิเสธทุก snapshot ที่ส่งเข้ามา** ไม่มีอะไร
บอกเลย เพราะ branch `STATUS2|` ใหม่เรียก `parseSnapshot()` แล้วทิ้งค่าที่คืนมาไปเฉย ๆ ต่างจาก
branch เก่า `STATUS|` ที่ print `serial status applied` ทุกครั้งที่สำเร็จ กว่าจะรู้ว่าพังคือหลัง
เพิ่ม log บรรทัดเดียวเข้าไปเช็ค accept/reject แล้วเห็นผลตั้งแต่รอบถัดไปทันที

## สาเหตุ

`gpt-6-astra` เขียน `main.cpp` ใหม่แล้วลบ `Serial.setRxBufferSize(4096)` หายไปเงียบ ๆ บอร์ดเลย
ตกกลับไปใช้ buffer default ของ Arduino ที่ 256 ไบต์ ขณะที่ record STATUS2 หนึ่งบรรทัดยาวราว
700 ไบต์ แถม loop ยังถอดรหัสเฟรม GIF ก่อนจะไปดูด UART อีก บรรทัดจึงมาไม่ครบทุกครั้ง กลายเป็น
JSON เพี้ยน → ถูกปฏิเสธ พิสูจน์ได้จากไฟล์ backup `main.cpp.bak-preastra-20260905-220349` ที่ยัง
มีบรรทัดนี้อยู่ ตัวที่ถูกเขียนใหม่ไม่มี

## บทเรียน

- **diff ที่รีวิวแค่ส่วนที่ "เพิ่ม" จะพลาดส่วนที่ "หาย"** โดยเฉพาะ setup ฮาร์ดแวร์บรรทัดเดียวที่ไม่มี
  ใครคิดว่าสำคัญ ต้อง diff ไฟล์เก่าหา call ที่แบกความถูกต้องไว้แล้วหายไปด้วย ไม่ใช่ดูแค่ logic ใหม่
  ว่าถูกไหม
- **อย่าทิ้งค่าที่ validator คืนมาเด็ดขาด** ถ้าทางเดินเก่าเคยประกาศความสำเร็จ แล้วทางใหม่เงียบ
  นั่นคือ regression ด้าน observability แม้โค้ดจะยังถูกต้องอยู่ก็ตาม — "host ส่งออกไปแล้ว" ไม่เท่ากับ
  "device รับเข้าไปจริง"
- **การขยาย wire format เปลี่ยนข้อกำหนดทางฟิสิกส์ไปด้วย** ข้อความ pipe เดิมยาวราว 250 ไบต์
  กลายเป็น JSON ยาวราว 700 ไบต์ ค่า buffer ที่เคยมีเหลือเฟือ กลายเป็นคอขวดจริงทันทีโดยไม่มีใคร
  ตั้งใจ

## ทางแก้ (สองชั้น)

1. `main.cpp` — ใส่ `Serial.setRxBufferSize(4096)` กลับก่อน `Serial.begin()`
2. `atom_status_bridge.py` — ส่งบรรทัดยาวเป็น chunk ละ 192 ไบต์ เว้น 20ms ไม่ให้พึ่งขนาด buffer
   อย่างเดียว
3. `codex_bridge.cpp` — branch STATUS2 log ผล applied/rejected ทุกครั้ง ไม่เงียบอีกต่อไป

ยืนยันสด: reject ที่ 22:37/22:38/22:39 แล้ว applied ตั้งแต่ 22:40/22:41/22:42 หลัง flash

## กฎที่ถอดได้ ใช้ซ้ำได้กว้างกว่าเคสนี้

1. ก่อนรับ AI rewrite ไฟล์ที่แตะฮาร์ดแวร์โดยตรง ให้ diff กับตัวเดิมมองหาบรรทัด setup ที่หายไป
   ไม่ใช่แค่เช็คว่า logic ใหม่ถูกไหม
2. ทุก branch ที่รับข้อมูลเข้าต้อง log ผลของ validator เสมอ ไม่ว่าจะ accept หรือ reject —
   ความเงียบไม่ใช่ทางเลือกที่ปลอดภัย
3. เปลี่ยนขนาด payload บนสาย ให้ทบทวน buffer/timing ที่ผูกกับขนาดเดิมทุกจุด อย่าคิดว่ามันยังพอ
   เหมือนเดิม
