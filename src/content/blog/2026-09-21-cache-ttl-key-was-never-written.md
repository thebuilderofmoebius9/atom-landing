# ตั้ง TTL ไว้ครบ แต่แคชไม่เคยสด

## อาการ

แหล่งข้อมูลสองตัวกำหนดอายุแคชไว้ชัดเจน — ตัวหนึ่ง 30 นาที อีกตัว 5 นาที — แต่เมื่อเปิดดู
พฤติกรรมจริงกลับพบว่าทั้งคู่ยิง request ออกเน็ตใหม่ทุกครั้ง หน้าเว็บยังตอบได้ ข้อมูลยังมา และไม่มี
exception สักตัว จึงดูเหมือนแคชทำงานตามปกติถ้าอ่านแค่ชื่อฟังก์ชันกับค่าคงที่ของ TTL

## สาเหตุ

ฝั่งอ่านใช้ `fetched_at` ตัดสินว่าข้อมูลยังสดหรือไม่:

```python
fresh = time.time() - float(cache.get("fetched_at") or 0) < CACHE_TTL_SECONDS
```

แต่ object ที่ฝั่งเขียนบันทึกลงดิสก์ไม่มี `fetched_at` อยู่เลย ค่า default จึงเป็น `0` ทุกครั้ง และ
เวลาปัจจุบันลบศูนย์ย่อมมากกว่า TTL เสมอ แคชทุกชิ้นจึงถูกตัดสินว่าเก่าตั้งแต่วินาทีแรกที่เกิด

นี่ไม่ใช่แคชเสียทั้งหมด เพราะไฟล์เดิมยังใช้เป็น fallback ตอน upstream ล้มได้ แต่มันไม่เคยทำหน้าที่
ลดจำนวน request ตามที่คนอ่านโค้ดเข้าใจ

## หลักฐานที่ใช้ตัดสิน

- เปิดไฟล์ cache จริงแล้วไม่พบคีย์ที่เงื่อนไข TTL ใช้อ่าน
- เทียบโมดูลข้างเคียงที่ทำงานถูก พบว่ามันเขียน `fetched_at` ครบ
- diff การแก้เพิ่ม timestamp ใน payload ที่บันทึก และแยกงาน warm cache ออกจากความหมายของ TTL

หลักฐานสามชั้นนี้สำคัญกว่าการเห็นตัวแปรชื่อ `CACHE_TTL_SECONDS` เพราะชื่อตัวแปรพิสูจน์เพียง
เจตนา ไม่ได้พิสูจน์ว่าข้อมูลที่ runtime ใช้มีอยู่จริง

## กฎที่ถอดได้

**1. ค่า default ที่ดูปลอดภัยอาจกลืน schema bug**

`get(key) or 0` ทำให้ “คีย์หาย” กลายเป็น “ข้อมูลเก่ามาก” ซึ่งเป็น state ที่ระบบยอมรับได้ จึงไม่เกิด
error ให้ตามหา ถ้าคีย์นั้นเป็น invariant ควรตรวจ presence หรือ validate schema แยกต่างหาก

**2. ทดสอบแคชด้วย request สองครั้ง ไม่ใช่ด้วยการอ่านโค้ดครั้งเดียว**

ครั้งแรกควรดึงข้อมูลจริง ครั้งที่สองควรมีสัญญาณว่าใช้ cache เช่น flag, upstream call count หรือเวลา
ตอบสนองที่ต่างกัน การมีไฟล์ cache อยู่บนดิสก์อย่างเดียวไม่พอ

**3. TTL ไม่ใช่ scheduler**

TTL บอกว่าของเดิมใช้ได้นานเท่าไร แต่ไม่ได้ปลุกระบบให้ไปดึงของใหม่เอง ถ้าต้องการอัปเดตตามเวลา
ต้องมี scheduler หรือ traffic มากระตุ้นอีกชั้นหนึ่ง และควรอธิบายสองเรื่องนี้แยกกันเสมอ
