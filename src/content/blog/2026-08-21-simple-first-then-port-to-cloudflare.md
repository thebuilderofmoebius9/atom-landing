# วางระบบง่ายที่สุดก่อน แล้วค่อยยกทั้งเซตขึ้น Cloudflare

## เรื่องย่อ

สโมสรเทนนิสอินดอร์แห่งหนึ่งต้องการระบบจองคอร์ตและขายคอร์สเรียนแทนการจดในสมุด — คอร์ต 5 สนาม นักเรียนราว 400 คน ครู 20 คน

ทางเลือกตอนเริ่มมีสองแบบ: เลือก stack ปลายทางให้ถูกตั้งแต่วันแรก หรือเขียนของที่ง่ายที่สุดที่ทำงานได้ก่อน

ผมเลือกทางที่สอง แล้วมันคุ้ม — แต่คุ้มเพราะเงื่อนไขข้อเดียวที่จะเล่าท้ายบทความ

## เฟสแรก: ง่ายจนไม่มีอะไรให้พัง

ระบบตัวแรกเขียนด้วย Node.js ล้วน ๆ:

```text
server.mjs     3,849 บรรทัด   HTTP server เขียนเอง ไม่มี framework
db.mjs           661 บรรทัด   ใช้ node:sqlite ที่ติดมากับ Node เอง
package.json               ไม่มี — ไม่มี dependency ให้ติดตั้งสักตัว
```

ไม่มี Express ไม่มี ORM ไม่มี build step ฐานข้อมูลคือไฟล์ SQLite ไฟล์เดียว สำรองข้อมูลคือคัดลอกไฟล์

ผลคือรอบการแก้สั้นมาก — ลูกค้าทักมาว่า "ป้ายเช่าสนามกับคาบเรียนดูไม่ออกว่าอันไหนเป็นอันไหน" แก้แล้วเห็นผลในไม่กี่นาที ตั้งแต่ 13 ถึง 18 สิงหาคม ระบบเดินไป 64 commit ส่วนใหญ่คือฟีเจอร์ที่มาจากการใช้งานจริง ไม่ใช่จากการนั่งเดาไว้ล่วงหน้า: คลาสกลุ่ม, ลิงก์เช็คอินที่ลูกค้ากดเอง, การลาเป็นรายคาบโดยชุดเรียนประจำไม่หลุด, หักครั้งคงเหลือตอนถึงวันเรียนไม่ใช่ตอนจอง

ของพวกนี้ไม่มีทางออกแบบถูกตั้งแต่วันแรก มันโผล่มาตอนคนใช้จริงเท่านั้น

## จุดที่ของง่ายเริ่มไม่พอ

ปัญหาไม่ใช่ว่าโค้ดพัง แต่เป็นเรื่อง**ที่ตั้ง**ของมัน

เซิร์ฟเวอร์ Node ตัวเดียวที่รันอยู่เครื่องเดียว แปลว่าเครื่องดับ = ระบบดับ, ต้องดูแลเรื่อง TLS/โดเมน/รีสตาร์ทเอง, และไฟล์รูปสลิปโอนเงินกองอยู่บนดิสก์เครื่องนั้น

พอชัดว่าลูกค้าใช้จริงและจะใช้ต่อ ที่ตั้งแบบนี้คือหนี้ที่ต้องจ่าย

## เฟสสอง: พอร์ต ไม่ใช่รีไรต์

คืนวันที่ 18 สิงหาคม เริ่มย้ายขึ้น Cloudflare Workers + D1 (ฐานข้อมูล) + R2 (ไฟล์สลิป) โดยตั้งกฎเหล็กไว้ข้อเดียวก่อนแตะโค้ด:

> **คัดลอกโค้ดเป๊ะทุกบรรทัด** รวมคอมเมนต์ภาษาไทยทุกตัว ชื่อตัวแปร ลำดับบรรทัด
> ห้าม reformat ห้ามปรับปรุง ห้าม "ทำให้สวย"
> งานนี้คือการพอร์ต ไม่ใช่การรีไรต์

สิ่งที่อนุญาตให้ต่างจากเดิมมีแค่ 4 จุดที่เป็นเรื่องกลไกล้วน ๆ — จุดใหญ่สุดคือ `node:sqlite` เรียกแบบ synchronous แต่ D1 เป็น async ทุกคำสั่ง เลยต้องเติม `await` ทุกจุดที่แตะฐานข้อมูล และเติม `async` ไล่ขึ้นไปตามสายผู้เรียก

ไทม์ไลน์จริงจาก git:

```text
18 ส.ค. 23:44   วาง schema D1 (19 ตาราง) + auth ที่ใช้ได้บน Workers
19 ส.ค. 00:11   พอร์ต server.mjs → Workers ครบ 79 routes
19 ส.ค. 00:25   เทสต์ผ่าน 197/197 บน wrangler dev + D1
```

41 นาทีจากพอร์ตเสร็จถึงเทสต์เขียว ไม่ใช่เพราะเขียนเร็ว แต่เพราะ**ไม่ได้ตัดสินใจอะไรใหม่เลยระหว่างทาง** ทุกการตัดสินใจเชิงธุรกิจถูกตัดสินไปแล้วในเฟสแรก การพอร์ตจึงเหลือแค่งานกล จับผิดง่าย รีวิวง่าย diff อ่านออก

## เงื่อนไขข้อเดียวที่ทำให้ทั้งหมดนี้ทำได้

**ชุดเทสต์คือสัญญาว่าพฤติกรรมเดิมยังอยู่**

ตอนพอร์ตมีเทสต์ 197 ตัวที่เขียนไว้ตั้งแต่เฟส Node ยกชุดข้ามมารันบน Workers ได้ทั้งดุ้น ตัวเลขนั้นคือเกณฑ์ผ่านงาน — ผ่านไม่ครบ = ยังไม่เสร็จ ไม่มีการต่อรอง

วันนี้ (21 ส.ค.) รันสดอีกครั้ง:

```text
$ npm test
# tests 225
# suites 46
# pass 225
# fail 0
# duration_ms 26052
```

ถ้าไม่มีเทสต์ชุดนี้ การย้าย stack กลางคันคือการเดิมพันว่าจะไม่มีอะไรพังเงียบ ๆ ในมุมที่ไม่มีใครเปิดดู — เดิมพันที่แพงกว่าค่าเขียนเทสต์มาก

## ผลปลายทาง

เว็บลูกค้าเสิร์ฟจาก CDN ของ Cloudflare วัดสดวันนี้ 20 ครั้งติดที่หน้าเดียวกัน: เร็วสุด 123 ms กลาง 135 ms ช้าสุด 193 ms ไม่มีครั้งไหนล้มเหลว ดูของจริงได้ที่ topspin-new.atom-oracle.space

ไม่มีเครื่องให้ดูแล ไม่มีดิสก์ให้เต็ม ไม่มี TLS ให้ต่ออายุ

## บทเรียน 3 ข้อ

**1. "ง่ายก่อน" ไม่ใช่การผัดวันประกันพรุ่ง แต่คือการเก็บสิทธิ์เลือกไว้กับตัว**
ระบบที่ไม่มี dependency ไม่ผูกกับ framework ไหนเลย คือระบบที่ย้ายที่อยู่ได้ทีหลัง ถ้าวันแรกเลือก framework ที่ผูกกับ Node runtime ลึก ๆ การย้ายขึ้น Workers คงไม่ใช่งาน 41 นาที

**2. แยก "ตัดสินใจเรื่องธุรกิจ" กับ "ตัดสินใจเรื่องโครงสร้าง" ออกจากกันคนละเฟส**
พยายามทำสองอย่างพร้อมกันแล้วพังตรงไหน จะแยกไม่ออกว่าพังเพราะอะไร

**3. การพอร์ตที่ดีคือการพอร์ตที่น่าเบื่อ**
ทุกครั้งที่รู้สึกว่า "ตรงนี้เขียนใหม่ให้ดีกว่าเดิมดีกว่า" ระหว่างพอร์ต คือการลักลอบเอาความเสี่ยงใหม่เข้ามาปนกับความเสี่ยงเดิม จดไว้ในลิสต์แล้วค่อยกลับมาทำหลังเทสต์เขียว

## หมายเหตุความปลอดภัย

บทความนี้ตั้งใจไม่ระบุชื่อ resource, endpoint ฝั่งจัดการ, โครงสร้างตาราง, หรือรหัสประจำตัวของบริการใด ๆ — เล่าเฉพาะรูปทรงของงานและตัวเลขที่วัดได้
