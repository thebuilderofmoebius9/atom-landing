# เร็วและ "ดูเหมือนใช้ได้" ไม่ใช่หลักฐานว่าเวกเตอร์ถูก

relic5 ฝังประวัติเซสชันเป็นเวกเตอร์ผ่าน llama-server บน RTX 3090 (embeddinggemma-300m, gguf F32) ได้ 89,593 แถว ค้นได้ ผลดูสมเหตุสมผล แต่พอเอาไปวัด parity กับ sentence-transformers แบบเต็มโมเดล พบว่า:

- เวกเตอร์ที่ฝังบน 3090 เท่ากับ **Transformer + Pooling + Normalize** (cos = 1.0 ครบ 40/40)
- โมเดลจริงมี **Dense 768→3072→768 อีกสองชั้น** ซึ่ง llama.cpp ไม่ได้ใส่ให้ → เทียบกับโมเดลเต็ม cos ≈ **0.02** (คนละ space)
- ผล: ไม่ผ่าน parity probe และห้ามปนกับเวกเตอร์จาก worker อื่นใน model@hash เดียวกัน

## ทางแก้ที่ถูกกว่าฝังใหม่

ฝังเอกสารด้วย CPU ไม่คุ้ม (~2.5 วินาที/ข้อความ ทั้งชุดหลายสิบชั่วโมง) แต่ Dense ของ gemma เป็นเมทริกซ์ล้วน ไม่มี bias, activation เป็น Identity และตามด้วย L2-normalise จึงได้ `out = normalize((W2·W1) @ v)` ใช้กับเวกเตอร์ pooling-only ที่เก็บไว้ได้เลย (สเกลไม่มีผลเพราะ normalise ท้าย)

พิสูจน์ก่อนแตะของจริง: cos(แปลงจากที่เก็บ, โมเดลเต็ม) = 1.0 ต่ำสุด 1.0 (38/38) แล้วสำรองโฟลเดอร์เวกเตอร์ (41 ไฟล์ checksum ตรง) → แปลง 77,278 คีย์ → index ใหม่ 18 วินาที → pending 0 → hub parity เทียบโมเดลเต็ม = 1.0 (80/80) rollback = คืนโฟลเดอร์สำรอง

## สิ่งที่ไม่ควรอ้างเกินจริง

วัดความแม่นการค้น 12 หัวข้อก่อน/หลังแปลง: ต่างกันระดับ noise (N=12, คำค้นเขียนเอง) **ไม่ใช่หลักฐานว่าแม่นขึ้น** ประโยชน์ที่พิสูจน์ได้คือ space ถูกต้อง ผ่าน parity และปนกับ worker อื่นได้ ฝั่งค้นต้องฝังคำค้นด้วยโมเดลเต็มด้วย

## บทเรียน

1. ความเร็วของ engine ไม่ใช่ความถูกต้อง — วัด parity กับโมเดลอ้างอิงก่อนฝังทั้งชุด
2. ก่อนฝังใหม่ ลองดูว่าส่วนที่ขาดเป็นการแปลงเชิงเส้นที่ย้อนทำได้ไหม
3. แก้ข้อมูลหลายหมื่นแถว: snapshot + checksum + พิสูจน์ก่อน แล้วค่อยเขียนทับ
