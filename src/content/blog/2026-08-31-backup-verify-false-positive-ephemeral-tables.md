# การ์ดตรวจแบ็กอัพเจอแถวหาย 100% แล้วเตือนไปว่าข้อมูลหาย ทั้งที่ควรว่างอยู่แล้ว

## เคสจริง

`topspin-backup.service` ล้มเหลว 03:30 น. — `topspin_backup_verify.py` เจอ `login_states`
ลดจาก 4 → 0 แถว (100%) เทียบกับแบ็กอัพเมื่อวาน จึงตัดสินว่า "ข้อมูลหาย ห้ามนับว่าสำรองสำเร็จ"

ตรวจ schema แล้วพบว่า `login_states` และ `sessions` เป็นตารางเก็บ **สถานะชั่วคราวที่มี
`expires_at` เป็น TTL และมี cron ลบทิ้งเองตามปกติ** (`DELETE FROM login_states WHERE expires_at <= ?`
ที่ `src/helpers.js:1126`) จำนวนแถวใกล้ 0 อยู่แล้วโดยธรรมชาติ — ลูกค้า 4 คนที่ล็อกอิน LINE
ค้างไว้ตอนแบ็กอัพเมื่อวาน แค่ state หมดอายุไปเองก่อนคืนนี้เท่านั้น ไม่ใช่ข้อมูลหาย

## กฎที่ได้

Guard ที่เทียบสัดส่วนแถวหายระหว่างสองแบ็กอัพ (กันเคส "ไฟล์ไม่ว่างแต่ข้อมูลหายบางส่วน") ต้อง
**แยกตารางออกเป็นสองกลุ่มตั้งแต่ต้น**:

- **ตารางข้อมูลธุรกิจถาวร** (bookings, customers, courts, users, …) — เทียบสัดส่วนแถวหายได้จริง
  เพราะโตขึ้นเรื่อย ๆ ตามธรรมชาติ ลดฮวบ = สัญญาณจริง
- **ตารางสถานะชั่วคราวที่มี TTL/cron ลบเอง** (login_states, sessions, …) — แกว่งไปมาใกล้ 0
  เป็นเรื่องปกติ ต้อง **ยกเว้นจากการเทียบสัดส่วน** ไม่ใช่ทำ threshold หลวมขึ้น เพราะ threshold
  ไหนก็ผิดได้ถ้าฐาน (old_n) ต่ำมาก — เช่น 4→0 คือ 100% เสมอไม่ว่า MAX_DROP_RATIO จะตั้งเท่าไหร่

วิธีระบุว่าตารางไหนเป็น "ชั่วคราว": มีคอลัมน์ `expires_at` เป็น TTL + มี cron/helper ที่ยิง
`DELETE ... WHERE expires_at <= ?` ตรง ๆ ในโค้ด — เช็คจาก schema.sql + grep โค้ดจริง ไม่ใช่เดา

## ทำไมเรื่องนี้สำคัญกว่าแค่เคสเดียว

การขยับ threshold ให้หลวมขึ้นเป็นทางแก้ที่ดูง่ายแต่ผิด เพราะมันทำให้การ์ดอ่อนลงสำหรับ
**ทุกตาราง** รวมถึงตารางธุรกิจถาวรที่ควรตรวจเข้มเหมือนเดิม ทางแก้ที่ถูกคือแยกประชากรตาราง
ตั้งแต่ชั้น input ของการวัด ไม่ใช่ปรับตัวเลขที่ปลายทาง — หลักการเดียวกับที่เจอในบั๊กวัดผล
อีกเคสของสัปดาห์นี้: พารามิเตอร์ของตัววัดต้องถูกบันทึกและตรวจสอบแยกจากตัวข้อมูลที่วัด

## การแก้ไข

`scripts/topspin_backup_verify.py` — เพิ่ม `EPHEMERAL_TABLES = {"login_states", "sessions"}`
แล้ว skip ตารางกลุ่มนี้ในลูปเทียบสัดส่วน (ไม่ตัดออกจากการนับตาราง/รายงานอื่น ๆ)

Negative test ก่อน deploy: จำลอง `bookings` หายเกลี้ยง (ตารางธุรกิจจริง) ยืนยันว่า guard ยังจับได้
(exit 1) — พิสูจน์ว่าการยกเว้นตารางชั่วคราวไม่ได้ทำให้ guard อ่อนลงสำหรับข้อมูลจริง
