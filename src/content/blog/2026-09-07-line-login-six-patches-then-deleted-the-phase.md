# ปะ LINE login 6 รอบใน 2 สัปดาห์ ก่อนจะรู้ว่าทางแก้จริงคือตัดช่วงที่เราคุมไม่ได้ทิ้ง

## อาการ

ลูกค้าที่ล็อกอินด้วย LINE บน `topspin-booking-workers` เจอปัญหาไม่หยุด: บางคนเจอ error
`state_mismatch` ทั้งที่ล็อกอินสำเร็จจริงไปแล้ว บางคนกดปุ่ม "เข้าสู่ระบบด้วย LINE" แล้วเงียบ ๆ
เด้งกลับหน้า login โดยไม่มีข้อความอะไรเลย และปัญหาเดิมย้อนกลับมาซ้ำเรื่อย ๆ — โค้ด callback ถูกแก้ไป
**6 commit ติดกันใน 2 สัปดาห์** เกือบทุกรอบเป็นการขยับตัวเลข/เพิ่มเงื่อนไขกู้ ไม่ใช่แก้เหตุ

## สาเหตุ — สองบั๊กคนละชั้นซ้อนกันอยู่

**ชั้นที่ 1 — `state_mismatch`**: webview ของ LINE ยิง callback ด้วย `state`+`code` เดิมซ้ำเป็น
พฤติกรรมปกติ (โหลดค้าง สลับแอปกลับมา กดย้อนกลับ) แต่โค้ดถือว่า state ใช้ได้ครั้งเดียวแบบเข้มงวด
callback ตัวที่สองจึงเป็น error เสมอ แต่ละรอบที่แก้คือ "ขยายเวลาที่ยอมให้กู้ได้" (30 วิ → 3 นาที)
ซึ่งเป็นการเดาเวลาที่ไม่มีวันถูกทุกเคส

**ชั้นที่ 2 — silent bounce**: คนละสาเหตุ คนละอาการ — คำขอไม่เคยถึงเซิร์ฟเวอร์เลย เพราะระบบ
ปฏิบัติการพา webview กลับก่อนจะยิง callback ได้จริง `audit_log` ไม่มีร่องรอยแม้แต่แถวเดียว ทั้งที่
ลูกค้ารายงานว่าเจอปัญหา

## ทางแก้เชิงราก — ทีละชั้น

**ชั้น state_mismatch**: เปลี่ยนจาก "กู้ภายใน N วินาที" เป็น idempotent ต่อคู่ `(state, code)` จริง ๆ
เก็บ `sha256(code)` ไว้ที่แถว state พอ callback ซ้ำมาด้วย code เดิม ก็ได้ผลเดิมเสมอไม่ว่าผ่านไปนาน
แค่ไหน — ไม่มีตัวเลข timeout ใหม่ให้ต้องมาจูนอีก สิ่งที่กัน replay จริงคือ "ต้องถือ code เดิมมาด้วย"
ไม่ใช่เวลา

**ชั้น silent bounce**: ย้ายจุดตรวจจับไปฝั่ง client เพราะเซิร์ฟเวอร์มองไม่เห็น — ตั้ง
`sessionStorage` ตอนกดปุ่ม เช็คตอนกลับมาหน้า login ว่ามี `?line=` ไหม ถ้าไม่มีและอยู่ในกรอบเวลาที่
ตั้งไว้ = bounce จริง แสดงข้อความให้ลูกค้ารู้ และยิง log เก็บหลักฐานไว้ให้รอบหน้าใช้แทนการเดา

**ชั้นสถาปัตยกรรม (ตัวที่ปิดจ๊อบจริง)**: ทั้งสองทางแก้ข้างต้นยังอยู่ในช่วงที่เราคุมได้ (ส่งออก /
รับกลับ) แต่ปัญหาจริงซ่อนอยู่ใน "ช่วงที่ระบบปฏิบัติการพา webview กลับ" ซึ่งเราไม่มีทางคุมได้เลย
ทางแก้ที่ปิดจ๊อบจริงคือเปลี่ยนไปใช้ **LIFF (LINE Front-end Framework)** แทน redirect flow —
SDK ให้ `id_token` มาในหน้าเดิมผ่าน `fetch` เลย ไม่มีการนำทางออกไปไหนอีก ความเงียบเป็นไปไม่ได้
อีกต่อไปโดยโครงสร้าง

## กับดักที่เกือบพลาดตอนย้ายไป LIFF

1. **`userId` ของ LINE ผูกกับ Channel ID ไม่ใช่ค่า global** — ต้องสร้าง LIFF app ใต้ channel เดิม
   เท่านั้น ถ้าสร้าง channel ใหม่ `sub` ที่ได้จะคนละค่า ลูกค้าเก่าทุกคนกลายเป็นคนใหม่ทันที
2. **CSP ตีตก SDK แบบเงียบ** ถ้าลืมเปิด `script-src` / `connect-src` ให้โดเมนของ LINE อาการจะ
   กลายเป็นบั๊กเดิมเป๊ะ — กดปุ่มแล้วไม่มีอะไรเกิดขึ้น
3. **ต้อง gate ด้วย env var เสมอ** — ยังไม่ตั้งค่า = ปุ่มยังทำงานแบบ redirect เดิมทุกประการ
   ของเดิมจึงไม่มีทางแย่ลงกว่าเดิมระหว่างย้าย

## กฎที่ถอดได้ ใช้ซ้ำได้กว้างกว่าเคสนี้

1. ถ้าต้องกลับมาปรับ timeout/threshold ตัวเดิมเป็นรอบที่สอง — หยุดปรับ แล้วถามว่าทำไมถึงต้องใช้
   เวลาเป็นเงื่อนไขตั้งแต่แรก
2. endpoint ที่ client ภายนอกยิงซ้ำได้เอง (webhook, OAuth callback, ปุ่มจ่ายเงิน) ต้องออกแบบให้
   idempotent ตั้งแต่ต้น โดยยึด key ของคำขอเอง ไม่ใช่ยึดเวลาที่คำขอมาถึง
3. ไม่มี log เลยไม่ได้แปลว่ายังหาไม่เจอ — แปลว่าคำขอไม่เคยมาถึง ต้องไปหาว่าใครถือพวงมาลัยอยู่ใน
   ช่วงนั้น
4. flow ที่ต้องพึ่ง redirect กลับ (OAuth, 3-D Secure, payment gateway) มีจุดตายที่ขา return เสมอ
   ถ้าเจอบั๊กซ้ำ ๆ ตรงนั้น ให้ถามว่ามีทางเลือกที่ไม่ต้อง redirect ไหม ก่อนจะปะเพิ่มอีกรอบ
