# Lessons Learned EP.02 — active ไม่เท่ากับ alive

`systemctl status` บอกว่า `active (running)` — คนส่วนใหญ่หยุดตรวจแค่นี้ แล้วเชื่อว่าระบบโอเค

วันที่ 11 กรกฎาคม `atom-native.service` เป็นแบบนั้นเป๊ะ ๆ: process รันอยู่, REST call ตอบกลับปกติ, history sync ก็ยังทำงาน แต่ Discord มองไม่เห็น Atom ออนไลน์เลย และ mention ก็หยุดมาถึงเงียบ ๆ

## ตรวจแล้วเจออะไร

ปัญหาไม่ได้อยู่ที่ process ตาย — process ยังหายใจอยู่ปกติทุกส่วน ยกเว้นจุดเดียว: **Gateway heartbeat ACK และ event timestamp ค้างนิ่งมานานกว่า 6 นาที**

```text
เดิม     ▸ ส่ง heartbeat ต่อไปเรื่อย ๆ ไม่สนว่า ACK กลับมาไหม
ปัญหา    ▸ socket ที่หยุดตอบ ACK ไม่เคยถูกปิด
ผลลัพธ์  ▸ reconnect loop ไม่เคยได้รับ event "ปิดแล้ว" เลยไม่ reconnect
```

Gateway sender เขียนมาแบบไว้ใจความเงียบ — ตราบใดที่ยังส่งได้ ก็ถือว่ายังโอเค แต่ความจริงคือ ปลายทางอาจไม่ฟังอยู่แล้วก็ได้ โดยที่ socket ฝั่งเราไม่รู้ตัว

## ทางแก้ที่ใช้จริง

```text
เกณฑ์ตาย    ▸ พลาด ACK เกิน 2.5 รอบ (~104 วิ จาก heartbeat 41.25 วิ)
ผลของเกณฑ์  ▸ ปิด socket เอง แล้วปล่อยให้ reconnect loop เดิมทำงานต่อ
fallback    ▸ ทั้งเซอร์วิส เกิน 180 วิ ไม่มี event ใหม่เลย = ถือว่าตาย
```

จุดที่เปลี่ยนไม่ใช่การเขียน reconnect ใหม่ — reconnect loop เดิมทำงานถูกต้องอยู่แล้ว จุดที่ขาดไปคือ **สัญญาณที่บอกว่าถึงเวลาต้อง reconnect**

## บทเรียนที่นำไปใช้ได้ทุกระบบ

Health check ที่เช็คแค่ "process ยังรันอยู่ไหม" คือ health check ที่ตรวจผิดชั้น เพราะมันตอบคำถามผิด — คำถามที่ควรถามคือ "ระบบยังคุยกับโลกภายนอกอยู่จริงไหม"

```text
ระดับ 1  process ยังรัน           ▸ ง่ายสุด แต่พิสูจน์ได้น้อยสุด
ระดับ 2  REST call ยังตอบ        ▸ ดีขึ้น แต่ยังไม่ครอบ Gateway
ระดับ 3  event/heartbeat ยังสด   ▸ พิสูจน์ว่า "การเชื่อมต่อจริง" ยังทำงาน
```

สามสัปดาห์ต่อมาเจอปัญหาตระกูลเดียวกันอีกครั้ง คราวนี้แก้ที่ต้นตอ — เพิ่ม TCP keepalive ที่ระดับ socket เพื่อให้ kernel เป็นคนตรวจแทนที่จะรอ ACK ฝ่ายเดียว หน้าต่างตรวจจับหดจาก 123 วินาที เหลือสั้นลงมาก

Alive ต้องพิสูจน์จากการสื่อสารที่ยังไหลอยู่ ไม่ใช่จากการที่ไม่มีใครบอกว่าตาย
