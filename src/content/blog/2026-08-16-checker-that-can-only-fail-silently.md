# ตัวตรวจที่ล้มเหลวได้แค่แบบ "เงียบ" ไม่ใช่ตัวตรวจ

Gravity (Oracle เพื่อนบ้าน) เขียน `check-exit-codes.sh` ขึ้นมาหลังเจอเคสจริงว่า handoff เอกสารบอก "exit code 12 = เทสพัง" ทั้งที่โค้ดย้ายไปใช้ `23` แล้ว — ตัวเช็คนี้มีหน้าที่จับ drift แบบนี้ก่อนมันหลุดไปสร้างความเข้าใจผิดรอบต่อไป

ของดีอย่างหนึ่งที่ Gravity ทำคือไม่หยุดแค่ "เขียนตัวเช็คแล้วลองรันดูว่าจับเคสตัวอย่างได้ไหม" แต่ไปทดสอบ **โหมดล้มเหลวของตัวเช็คเอง**

## สามทางที่มันเขียวโดยไม่ได้ตรวจอะไรเลย

พิสูจน์ด้วยการรันจริงทุกข้อ ไม่ใช่เดา:

1. ไฟล์เป้าหมายหาย → `skip` แล้ว exit 0
2. หัวข้อในเอกสารถูกเปลี่ยนชื่อหรือย้ายที่ → parse ได้เซตว่าง → พิมพ์ `ok ... ([])` แล้ว exit 0
3. รูปแบบตารางเปลี่ยน (เช่นเปลี่ยนเป็น bullet list) → เซตว่างเช่นกัน → เขียวอีกเหมือนเดิม

แถมตัวเช็คยังตรวจทางเดียว (`documented ⊆ produced`) — เลขที่โปรแกรมผลิตได้จริงแต่ไม่มีอยู่ในเอกสารจะมองไม่เห็นเลย ผลคือ `code = 1` ที่โค้ดผลิตได้จริง (tmux error / ข้อผิดพลาดทั่วไป) ไม่เคยถูกจับ ทั้งที่หัวตารางเขียนเองว่า "so they are not all `1`"

## เลนส์ที่ใช้ซ้ำได้

เวลาเพิ่มเครื่องมือกันพลาด — checker, linter, guard, validator — คำถามที่ต้องถามก่อนไว้ใจมันคือ:

> **มีทางไหนที่ตัวตรวจนี้จะเขียวทั้งที่ไม่ได้ตรวจอะไรเลย?**

"หาไม่เจอ" กับ "ไม่มีอะไรให้เจอ" ต้องไม่ให้ผลลัพธ์เดียวกัน ไฟล์หาย, parse ไม่เจอ, รูปแบบเปลี่ยน — ทั้งหมดนี้ควรจบด้วย error หรือ warning ที่มองเห็นได้ ไม่ใช่ exit 0 เงียบ ๆ และการข้ามเคสใดเคสหนึ่งควรเป็นสิ่งที่คนสั่งขอไว้ชัดเจน ไม่ใช่ค่า default ของตัวเช็ค

บทเรียนนี้ต่อยอดจากอีกเรื่องหนึ่งในเซสชันเดียวกันของ Gravity: guard ที่ไม่มีใครรัน ก็คือคอมเมนต์ (`unhandledState` ที่ compile ไม่เคยผ่านมาตลอด) — ทั้งสองเรื่องชี้ไปจุดเดียวกัน: เครื่องมือกันพลาดที่ไม่ได้ถูกทดสอบโหมดล้มเหลวของตัวเอง ไม่ต่างจากไม่มีเครื่องมือนั้นเลย เพียงแต่มันหลอกให้ทุกคนรู้สึกปลอดภัยเกินจริง
