# startsWith('/') ไม่ใช่ guard ของ redirect

## อาการ

เจอตอนรัน `/review` บนสาขาแก้ QA ของระบบจองคอร์ตเทนนิส — โค้ดกันปลายทาง redirect หลังล็อกอินไว้แบบนี้ อยู่ 4 จุดในโปรเจกต์:

```js
if (ret && ret.startsWith('/')) location.href = ret
```

เจตนาชัดเจน: "รับเฉพาะพาธในเว็บเรา อย่ารับ URL เต็มที่ชี้ไปเว็บอื่น"

## ทำไมถึงพัง

`//evil.com` **ก็ขึ้นต้นด้วย `/` เหมือนกัน** เงื่อนไขผ่านหมดทุกจุด

แต่เบราว์เซอร์อ่าน `//evil.com` เป็น **protocol-relative URL** — เติม protocol ปัจจุบันให้อัตโนมัติ
กลายเป็น `https://evil.com` ทันที ผู้ใช้ถูกพาออกนอกเว็บ

ที่อันตรายคือลิงก์หน้าตาดูเหมือนของเว็บเราทั้งดุ้น:

```text
ourdomain.com/login.html?return=//evil.com
```

โดเมนต้นทางถูกต้องจริง ผู้ใช้เห็นชื่อโดเมนที่คุ้นเคยในแถบที่อยู่ก่อนคลิก — เอาไปทำ phishing ได้ตรง ๆ

อีกตัวที่ต้องกันด้วยคือ `/\evil.com` เพราะบางเบราว์เซอร์ normalize backslash เป็น slash ก่อนตีความ URL

## ท่าที่ถูก

guard ตัวเดียว ใช้ร่วมทุกจุด อย่ากระจายเงื่อนไขไปเช็คทีละที่:

```js
const safeReturn = (v) =>
  (typeof v === 'string' && v.startsWith('/') && !v.startsWith('//') && !v.startsWith('/\\')) ? v : ''
```

## บทเรียนที่กว้างกว่าเคสนี้

**1. guard ที่เขียนจากเจตนา ไม่ใช่จากรูปแบบ input จริง จะมีรูเสมอ**
คำถามที่ต้องถามตอนเขียน guard ไม่ใช่ "เงื่อนไขนี้ตั้งใจกันอะไร" แต่คือ **"อะไรบ้างที่ผ่านเงื่อนไขนี้ได้"**
สองคำถามให้คำตอบต่างกันมาก — `startsWith('/')` "ตั้งใจ" กันได้ถูกทาง แต่ "ผ่านได้จริง" กว้างกว่าที่ตั้งใจ

**2. เจอ guard อ่อนที่จุดเดียว ให้ grep หาทุกจุดที่เขียนเงื่อนไขเดียวกันทันที**
เคสนี้เจอ 4 จุด ทั้งฝั่งหน้าเว็บและเซิร์ฟเวอร์ แก้จุดเดียวคือปะอาการ ไม่ใช่แก้ปัญหา

**3. ฟีเจอร์ที่ทำให้เส้นทางเก่าถูกใช้บ่อยขึ้น คือสัญญาณว่าถึงเวลา review เส้นทางนั้นใหม่**
รูนี้มีมาตั้งแต่แรกที่เขียนระบบล็อกอิน แต่ไม่มีใครเจอจนกระทั่งเพิ่มพารามิเตอร์ `?return=` เข้าไปในหน้าคอร์สเรียนใหม่ ทำให้เส้นทางนี้ถูกใช้งานถี่ขึ้นและถูกมองเห็น

## หมายเหตุความปลอดภัย

บทความนี้ตั้งใจไม่ระบุชื่อโดเมนจริง endpoint จริง หรือรายละเอียดที่พอเอาไปโจมตีระบบจริงได้ — เล่าเฉพาะรูปแบบของบั๊กและวิธีแก้ที่ใช้งานทั่วไปได้
