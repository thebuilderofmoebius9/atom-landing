# ขยาย timeout ถูกที่หนึ่ง ลืมอีกที่หนึ่ง

มีคำสั่งให้ "แก้ timeout เพิ่ม" และมันถูกทำจริง: `atom-native` ขยาย `timeout_seconds` จาก 1800 เป็น 3600 เมื่อ 2026-09-10 เพราะงานจริงใช้ 2,315 วินาที แต่ `chuda_bot.py` ยังเป็น `GROK_TIMEOUT = 180` งานยาวจึงตายซ้ำจนต้องถูกทักว่า "เคยบอกแล้ว"

## คอมเมนต์ที่ล็อกการตัดสินใจเก่า

```python
GROK_TIMEOUT = 180  # kept at 180 by design — option 1 (600s) rejected
```

คอมเมนต์นี้เก่ากว่าการตัดสินใจใหม่สองวัน แต่หน้าตาเหมือนมีคนคิดมาแล้ว คนอ่านทีหลังจึงข้าม มันกลายเป็นยามเฝ้าประตูให้ค่าที่ตายแล้ว

## ของจริงรันอยู่ที่ไหน

- description ของ `chuda.service` เขียนว่า "on onkhome" ทำให้เข้าใจว่ารันบนบ็อกซ์
- แต่ `systemctl --user show -p MainPID` + `ps` + log ที่ขยับจริง ยืนยันว่ารันบนเครื่องนี้
- ถ้าเชื่อ description แล้ว ssh ไปบ็อกซ์ที่ timeout จะสรุปผิดว่า "แก้ไม่ได้"

## สิ่งที่ทำ

- สำรองก่อนแก้ แล้วปรับ `GROK_TIMEOUT` 180 → 600 และ `PROGRESS_EVERY_S` 45 → 120
- แก้ docstring และ `AGENTS.md` ที่ยังเขียนนโยบาย 180 ให้ตรงกับโค้ด
- พิสูจน์หลังรีสตาร์ท: log ของ PID ใหม่แสดง `GROK_TIMEOUT=600 PROGRESS_EVERY_S=120`

## บทเรียน

- คอมเมนต์ที่บอกว่า "ตั้งใจเป็นแบบนี้ / ปฏิเสธ X แล้ว" ต้องมีวันที่กำกับ และเมื่อมีการตัดสินใจใหม่ต้องแก้คอมเมนต์ด้วย
- คำสั่งที่แตะค่าเดียวกัน ต้อง grep ทุก service ที่ใช้ค่านั้น ไม่ใช่แก้ที่แรกที่เจอ
- หา MainPID ก่อนเสมอ อย่าเชื่อ description ของ unit
