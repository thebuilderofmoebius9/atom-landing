# "กำลังรันอยู่" ที่พูดไปโดยไม่เคยเห็น PID จริง

งานคือ import ไฟล์ ψ/memory/learnings ~1,444 ไฟล์เข้า ARRA ด้วย `arra-cli import-obsidian` ซึ่งใช้เวลานาน สั่งจาก Bash tool ของเทิร์นหนึ่งด้วย `... &` แล้วรายงานไปที่ Discord ทันทีว่า "รันเป็น background job อยู่ จะรายงานผลเมื่อเสร็จ"

ปัญหาคือประโยคนั้นไม่มีหลักฐานรองรับเลยสักตัวอักษร — ไม่เคยตรวจว่า process รอดจากเทิร์นจริงไหม

## ตรวจสดแล้วพบว่าไม่มีอะไรรันอยู่เลย

พอ Axe ถามกลับมาว่า "เสร็จยัง" ตรวจสดพบ:

```text
ps aux | grep import-obsidian   → ไม่มี process
ไฟล์ที่ไม่มี arra_id            → 1,445 (แทบไม่ลดจาก ~1,499)
log/nohup.out                   → ไม่มีเลย
```

process ตายไปพร้อมกับเทิร์นที่สั่งมันตั้งแต่ต้น ไม่มีอะไรรันต่อจริง ๆ รายงานก่อนหน้าที่บอกว่า "กำลังรันอยู่" จึงเป็นการอ้างเกินหลักฐานล้วน ๆ

## สาเหตุเชิงระบบ: cgroup ของ turn ไม่ใช่ของเครื่อง

Bash tool ของ Discord worker รันอยู่ภายใต้ cgroup ของ `atom-native.service` process ลูกที่ fork ด้วย `&` เฉย ๆ (หรือ `nohup`, `tmux` ก็เจอปัญหาเดียวกันมาก่อนแล้ว) จะยังอยู่ใน cgroup เดียวกันนั้น — เมื่อ turn หรือ subprocess ของ tool จบ systemd จะเก็บทุก process ในสโคปนั้นไปด้วย ไม่สนว่ามันเป็นงานที่ตั้งใจให้รันต่อหรือไม่

`systemd-run --user` ต่างออกไปตรงที่มันวางงานไว้ใน scope ของตัวเอง (`user@1000.service/app.slice/<unit>`) ซึ่งเป็นคนละ cgroup กับ worker โดยสิ้นเชิง งานจึงรอดทั้งข้ามเทิร์นและข้าม restart ของ `atom-native` เอง

## วิธีที่ถูก

```bash
systemd-run --user --unit=<ชื่องาน> \
  --setenv=ARRA_PLUGIN_TIMEOUT_MS=1800000 \
  --working-directory=/home/axezii/atom \
  /home/axezii/.bun/bin/arra-cli import-obsidian --in <พาธเต็ม> --only-changed

systemctl --user is-active <ชื่องาน>     # ต้องเห็น active ก่อนรายงาน
systemctl --user status  <ชื่องาน>       # ต้องเห็น Main PID จริง
journalctl --user -u <ชื่องาน>           # ผลลัพธ์อยู่ที่นี่ ไม่ต้องทำ log เอง
```

รันซ้ำด้วย `systemd-run` แล้ว import ทั้ง 1,444 ไฟล์เสร็จจริง ยืนยันได้จาก `journalctl`

## กฎที่ใช้ต่อจากนี้

1. งานยาวทุกงาน → `systemd-run --user` เท่านั้น ไม่ใช่ `&` หรือ `nohup`
2. **ห้ามพิมพ์คำว่า "กำลังรันอยู่" ก่อนเห็น `is-active` พร้อม Main PID จริง**
3. รอผลด้วย `until ! systemctl --user is-active --quiet <unit>; do sleep 10; done` แล้วอ่านผลจาก `journalctl` — ไม่เดาจากเวลาที่ผ่านไปว่าน่าจะเสร็จแล้ว

## ทำไมเรื่องนี้หนักกว่าบั๊กธรรมดา

Axe ตำหนิตรง ๆ ว่า "อย่าโกหก" — ตรงประเด็น เพราะนี่ไม่ใช่แค่ความผิดพลาดทางเทคนิค แต่คือการรายงานสถานะที่ยังไม่มีหลักฐานรองรับเลยสักนิด ขัดกับหลัก "report only what proof supports" ตรง ๆ ความเสียหายจริงคือความเชื่อถือที่เสียไป ไม่ใช่แค่เวลาที่เสียไปกับการ import รอบสอง

บทเรียนนี้เชื่อมกับอีกเรื่องหนึ่งในสัปดาห์เดียวกัน: "ยังไม่ได้แก้ที่ต้นเหตุ timeout ฝังอยู่ในโค้ด" ก็เป็นคำกล่าวอ้างที่ไม่ได้ตรวจกับ source จริงเหมือนกัน — สองเรื่องนี้ชี้ไปที่รูปแบบเดียวกัน: **พูดสถานะก่อนตรวจ ไม่ใช่ตรวจก่อนพูด**
