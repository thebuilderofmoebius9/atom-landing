# index ดีขึ้นหนึ่งที่ อาจแย่ลงอีกสามที่

เพิ่ม index สองตัวเพื่อเร่งคิวรี "ประวัติ" ของหน้าสมาชิก วัดบนสำเนาฐานจริงแล้วลดจาก 155,156 เหลือ 786 แถวต่อคำขอ และผลลัพธ์ตรงกันทุกลูกค้า — ดูเหมือนจบ

แต่ตัววางแผนคิวรี (query planner) ไม่ได้เลือก index ตามที่เราตั้งใจ:

- **หน้ารายการลูกค้าของแอดมิน**: planner สลับลำดับ join จาก 453,565 แถว/149 ms เป็น 791,839 แถว/332–577 ms ต้องแก้ด้วย `INDEXED BY`
- **คิวรีหาหนี้ค้าง**: เงื่อนไข `customer_package_id IS NULL` ตรงกับราว 3,300 แถว planner เลยเลือก index ใหม่ อ่าน ~3,300 แถว ทั้งที่ index เดิมเหลือแค่ ~30 แถว

## สาเหตุรากเป็นเรื่องกระบวนการ

1. **วัดเฉพาะคิวรีเป้าหมาย** ไม่ไล่ "ทุกคิวรีที่มีเงื่อนไขตรงคอลัมน์ของ index ใหม่"
2. **สำเนาฐานมีค่าสถิติเก่า** — สถิติบอกตาราง 1,823 แถว ทั้งที่จริง 16,939 แผนบนสำเนาจึงไม่เหมือนฐานจริง ทำให้ทั้งประเมินว่าช้าลงทั้งที่ไม่ช้า และประเมินว่าไม่แย่ทั้งที่แย่
3. **ประเมินรอบ cron ผิด** — คิดว่ารันทุก 10 นาที ทั้งที่งานนั้นรันแค่ชั่วโมงละครั้ง

## ทำทุกครั้งที่เพิ่ม index

- grep ทุกคิวรีที่แตะตารางนั้น แล้ววัด `EXPLAIN QUERY PLAN` + แถวที่อ่านจริง **ก่อนและหลัง**
- วัดบนฐานจริง (หรือรัน `ANALYZE` บนสำเนาก่อน) ไม่เชื่อแผนจากสำเนาที่สถิติเก่า
- ตรวจจุดเรียกจริงว่ารันถี่แค่ไหน ก่อนตัดสินว่า "ช้าแต่ไม่เป็นไร"

ข้อสรุป: การเพิ่ม index คือการเปลี่ยนพฤติกรรมของทุกคิวรีบนตารางนั้น ไม่ใช่แค่คิวรีที่เราตั้งใจแก้
