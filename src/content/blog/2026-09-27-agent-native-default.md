# ก่อนสร้างฟีเจอร์ ต้องถามก่อนว่า agent-native ทำได้ไหม

## คำถามที่เปลี่ยนวิธีออกแบบ

ระบบสมัยนี้มีผู้ใช้มากกว่าคนที่กดปุ่มบนหน้าเว็บ บางงานถูกสั่งจาก Discord, CLI, API หรือ agent
ด้วย ถ้าแต่ละทางมี business logic ของตัวเอง ระบบจะค่อย ๆ แตกเป็นหลายความจริง: ทางหนึ่งแก้บั๊กแล้ว
อีกทางยังทำงานแบบเก่า และ state ที่ agent ต้องใช้กลับซ่อนอยู่ใน component state ที่อ่านไม่ได้

บทเรียนสัปดาห์นี้จึงตั้งกฎใหม่ว่า ก่อนออกแบบโปรแกรมหรือฟีเจอร์ใด ๆ ต้องประเมินก่อนว่า
ทำแบบ **agent-native** ได้ไหม ถ้าทำได้ ให้เริ่มจากรูปแบบนั้น ถ้าทำไม่ได้ ต้องระบุเหตุผลให้ชัด

## หลักการสามข้อ

ข้อแรกคือ **action เดียว หลายปาก** นิยาม operation หนึ่งครั้ง แล้วเปิดให้ UI, agent tool, HTTP,
MCP, A2A หรือ CLI เรียกใช้ได้ โดยไม่เขียนตรรกะคนละชุด

ข้อสองคือ **state ต้อง inspect ได้** เก็บ state สำคัญไว้ใน store ที่ agent อ่านและสอบย้อนกลับได้
อย่าซ่อนกติกาธุรกิจไว้ใน local state ของหน้าจอ เพราะผู้ใช้แบบอื่นจะต้องเดาจากผลลัพธ์แทนการอ่าน
สัญญาจริง

ข้อสามคือ **agent ต้องอยู่ใน contract เดียวกับคน** สิทธิ์ ขอบเขต และผลของ action ต้องใช้กฎเดียวกัน
agent ไม่ควรเป็นผู้ช่วยที่แปะข้างระบบและมีเส้นทางพิเศษของตัวเอง

## checklist ก่อนลงมือ

- capability นี้เขียนครั้งเดียวแล้วให้คนกับ agent เรียกได้หรือไม่
- state ที่ action แตะอยู่ในที่ที่ agent อ่านและตรวจสอบได้หรือไม่
- ถ้าคำตอบคือไม่ได้ ติดที่ boundary ใด และเหตุผลนั้นถาวรพอหรือไม่

กฎนี้ไม่ได้บังคับให้ทุกอย่างต้องเป็น API ใหญ่ตั้งแต่วันแรก จุดเริ่มต้นอาจเป็น template ที่รันได้จริง
แล้วค่อยตัดให้ตรงงาน แต่ต้องวาง capability และ state ไว้ในจุดที่เปิดให้ผู้ใช้ทุกประเภทเข้าถึงได้
ตั้งแต่ต้น นั่นลดงานซ้ำและทำให้การตรวจสอบภายหลังเป็นส่วนหนึ่งของการออกแบบ ไม่ใช่งานเก็บกวาด
