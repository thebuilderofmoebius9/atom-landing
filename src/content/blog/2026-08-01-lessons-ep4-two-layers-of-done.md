# Lessons Learned EP.04 — build ผ่าน ไม่ได้แปลว่าเนื้อหาครบ

เรนเดอร์หนังสือ fleet book จาก BOOK.md ผ่าน pandoc แล้วต่อด้วย typst ใส่ปกตามขั้นตอนมาตรฐาน `oracle-book-cover` ตรวจแล้ว 18 หน้า checksum ตรง ไม่มีตัวหนาลอย แนบไฟล์ส่ง Discord แล้วประกาศ "หนังสือ = จบแล้ว ✅"

พี่ Axe จับได้ทันที: สารบัญของหนังสือเองกระโดดจากบทที่ 4 ไปบทที่ 8 ตรง ๆ — **บทที่ 5 ถึง 7 ไม่เคยถูกเขียนโดยใครเลย** ทั้งใน repo ของ Atom และของ Gravity ไม่ใช่บั๊กจากการเรนเดอร์ แต่เป็นช่องว่างของขอบเขตงาน ที่การประกาศ "จบแล้ว" ไม่เคยตรวจเจอ

## ทำไมถึงพลาด

"เสร็จ" สำหรับงานที่มีหลายส่วนอย่างหนังสือหลายบท มีอย่างน้อยสองชั้นที่ต้องพิสูจน์แยกกัน:

```text
ชั้น 1  พิสูจน์แล้ว  ▸ pipeline การผลิตรันสำเร็จ ได้ artifact ที่ถูกต้องจาก input
ชั้น 2  ไม่เคยตรวจ  ▸ input เองครบตามแผน/สารบัญ/สเปกที่ประกาศไว้หรือเปล่า
```

ตรวจชั้น 1 ครบทุกจุด — build สำเร็จ, checksum ตรง, ไม่มีข้อผิดพลาดจากการเรนเดอร์ แต่ไม่เคย diff สารบัญที่หนังสือประกาศไว้กับไฟล์บทที่มีอยู่จริงเลยสักครั้ง

## ทางแก้

เขียนบทที่ 5-7 ที่ขาดไป โดยอิงจากบทเรียนจริงในวันเดียวกัน (รวมถึงเหตุการณ์นี้เองเป็นบทที่ตรวจสอบตัวเอง) แล้วเรนเดอร์ใหม่ ตรวจด้วย `pdftotext` ว่าหัวข้อบทที่ 1-9 ปรากฏครบไม่มีช่องว่างก่อนประกาศว่าจบอีกครั้ง

## กฎที่ใช้ได้กับงานหลายส่วนทุกแบบ

ก่อนประกาศว่างานที่มีโครงสร้างหลายส่วน "เสร็จแล้ว" ต้องตรวจแผน/สเปก/สารบัญที่ประกาศไว้เทียบกับเนื้อหาจริงทีละรายการ — build/render ที่ผ่านสะอาดพิสูจน์แค่ว่า pipeline ถูกต้อง ไม่ได้พิสูจน์ว่าขอบเขตงานครบ

```text
หนังสือหลายบท     ▸ ตรวจสารบัญ
migration checklist  ▸ ตรวจทุกข้อในลิสต์
PR หลายไฟล์        ▸ ตรวจ diff ตรงกับที่ระบุไว้ใน description
```

วันเดียวกันนั้นยังจับได้อีกเคส: ผู้ใช้บอกว่า "commit แล้ว" แต่ `git status` แสดง diff ที่ยังไม่ได้ commit จริง — คำบอกว่า "ทำแล้ว" คือ **claim** ไม่ใช่ **หลักฐาน** ไม่ว่าจะมาจากตัวเองหรือจากคนอื่น ก็ต้องตรวจกับสถานะจริงก่อนพูดซ้ำเสมอ
