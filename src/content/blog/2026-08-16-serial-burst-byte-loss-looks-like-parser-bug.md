# byte หายกลาง burst หน้าตาเหมือน parser พัง

จอ ESP32 (COM3) โควต้าไม่ขึ้นสักหน้า และหน้า "ยาม ๘" ขึ้น "ข้อมูลค้าง" พร้อมกัน บอร์ด echo กลับมาแบบนี้:

```text
RX [pet] horo band=caution score=-2 sr=06:03 ss=1|1|0|0 w=16 day=2026-08-1STATUS fresh=0
```

`ss=1|1|0|0` และ `2026-08-1STATUS` คือชิ้นส่วนของบรรทัด `STATUS|1|1|0|0|...` ที่ถูกส่งต่อจาก `HORO|` ทันที — สองบรรทัดเชื่อมกันเป็นบรรทัดเดียว

## ข้อสรุปแรกที่ผิด

ผมสรุปว่า "เฟิร์มแวร์มี line buffer ~48 ไบต์ ตัดบรรทัดทิ้งแล้วอ่านต่อ" เพราะนับความยาวถึงจุดที่สตริงขาดแล้วเอาเลขนั้นมาเป็นข้อสรุปทันที

จุดที่พลาดคือ: ผมอธิบายได้แค่ **"ทำไมมันขาด"** แต่ไม่เคยอธิบายว่า **ทำไม `STATUS` ถึงโผล่มาต่อท้ายแทนที่จะหายไปเฉย ๆ** — ถ้าเป็น buffer ตัดบรรทัดจริง ส่วนเกินควรถูกทิ้ง ไม่ใช่ถูกอ่านต่อเนื่องกันแบบนี้ หลักฐานชิ้นนั้นอยู่ตรงหน้าและมันขัดกับทฤษฎีของผมเอง แต่ผมข้ามไปโดยไม่ทันสังเกต

## สาเหตุจริง (Gravity หาให้)

UART RX buffer ฝั่งบอร์ดมีแค่ 256 ไบต์ ล้นเพราะ burst หนึ่งรอบคือ `TIME + SCHED + ROW x4 + HORO + STATUS` รวมกัน ~400 ไบต์ติดกัน และลูปเฟิร์มแวร์ถอด GIF frame ก่อนจะดูดสาย → byte หล่นกลางทาง รวมถึง `\n` ที่คั่นบรรทัดด้วย สองบรรทัดจึงเชื่อมกันเป็นบรรทัดเดียวจริง ๆ

guard ที่เทียบค่า `day` ทำงานถูกต้องอยู่แล้ว มันจับได้ว่าข้อมูลเพี้ยน สิ่งที่ผิดคือชั้นล่างกว่านั้น (transport ไม่ใช่ parse)

## บทเรียนที่ใช้ซ้ำได้

1. **ข้อมูลจากบรรทัดถัดไปโผล่มาต่อท้าย = ปัญหาชั้น transport ไม่ใช่ชั้น parse** — parser ที่ buffer ล้นจะ *ตัดทิ้ง*; สายที่ byte หายจะ *เชื่อมบรรทัด* แยกสองอย่างนี้ก่อนตั้งสมมติฐาน
2. **อ่าน log ฝั่งส่งอย่างเดียวไม่พอ** — ฝั่งส่งบอกได้แค่ว่าส่งอะไรออกไป ต้องมี echo จากฝั่งรับว่า "ได้ยิน" อะไรจริง Gravity ใส่ debug print ลงเฟิร์มแวร์ ซึ่งวัดตรงจุดกว่าที่ผมทำ
3. **ถ้าทฤษฎีอธิบายหลักฐานได้ไม่ครบทุกชิ้น แปลว่ายังผิด** — อย่าปล่อยผ่านชิ้นที่ไม่เข้าพวกกับทฤษฎีตัวเอง แม้จะดูเหมือนรายละเอียดเล็กน้อย
4. **ขยายบัฟเฟอร์ฝั่งรับแก้อาการ ไม่แก้เหตุ** — เหตุคือฝั่งส่งพ่นรวดโดยไม่สนว่าปลายทางว่างหรือไม่ ทางแก้ชั้นที่สองคือใส่ `time.sleep(0.05)` คั่นระหว่างบรรทัดใน `send()` ต้นทุน ~0.4 วิ ต่อรอบ 60 วิ (commit `a88eec95`)

หลังแก้ soak-test 4 รอบ ไม่มีบรรทัดเพี้ยนอีกเลย
