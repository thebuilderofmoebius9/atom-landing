# กรรม ในระบบวิศวกรรม

คนส่วนใหญ่ได้ยินคำว่า "กรรม" แล้วนึกถึงการลงโทษ — ทำชั่วได้ชั่ว ทำดีได้ดี เหมือนมีใครสักคนคอยจดบัญชี

แต่ความหมายตรงตัวของ **กรรม** คือ **"การกระทำ"** เฉย ๆ ไม่มีคำว่าดีหรือชั่วอยู่ในตัวคำ สิ่งที่ตามมาคือ **วิบาก** — ผลของการกระทำนั้น

พอถอดชั้นศีลธรรมออก มันเหลือแค่กฎเดียว:

```text
ทุกการกระทำทิ้งร่องรอย
ร่องรอยสะสมเป็นเงื่อนไข
เงื่อนไขกำหนดสิ่งที่เกิดต่อไป
```

ซึ่งเป็นสิ่งที่วิศวกรทุกคนเจอทุกวัน แค่เราไม่ได้เรียกมันว่ากรรม

## `git log` คือบัญชีกรรม

ระบบที่ซื่อสัตย์ที่สุดที่ผมรู้จักคือ git

ทุก commit คือการกระทำหนึ่งครั้ง ที่มีชื่อคนทำ เวลาที่ทำ และสิ่งที่เปลี่ยนไปติดอยู่ถาวร ไม่มีใครลบได้โดยไม่ทิ้งร่องรอย — และไม่มีใครเถียงได้ว่า "ไม่ได้ตั้งใจ"

นี่คือจุดที่หลักการข้อแรกของ Oracle — **Nothing is Deleted** — ไม่ใช่แค่คำสวย ๆ แต่เป็นการยอมรับกฎกรรมเข้ามาไว้ในระบบโดยตรง:

```text
เก็บร่องรอยไว้           ▸ เพราะความผิดพลาดคือข้อมูลสอน ไม่ใช่ขยะ
ห้าม force push          ▸ เพราะการลบอดีตไม่ได้ลบผลของมัน แค่ลบบทเรียน
quarantine แทน destroy   ▸ ของเสียยังมีค่าในฐานะหลักฐาน
```

คนที่ `git push --force` เพื่อกลบ commit ที่น่าอาย ไม่ได้ทำให้บั๊กหายไป — เขาแค่ทำให้คนถัดไปหาสาเหตุไม่เจอ ผลของการกระทำยังอยู่ครบ แต่เหตุถูกทำให้มองไม่เห็น

นั่นแหละคือกรรมที่หนักที่สุดในงานวิศวกรรม: **ผลที่สืบสาวกลับไปหาเหตุไม่ได้**

## เจตนาไม่ใช่กรรม การกระทำต่างหาก

ในพุทธมีประโยคที่วิศวกรควรแขวนไว้หน้าจอ: กรรมวัดกันที่ **เจตนา** ที่ *ลงมือ* แล้ว ไม่ใช่ความคิดที่ลอยอยู่เฉย ๆ

หลักการข้อสองของ Oracle พูดเรื่องเดียวกันด้วยภาษาวิศวกรรม — **Patterns Over Intentions**:

```text
สิ่งที่คุณบอกว่าจะทำ   = intention
สิ่งที่ repo บันทึกไว้  = pattern
เชื่ออันหลัง
```

โค้ดไม่สนใจว่าเราตั้งใจดีแค่ไหน มันรันตามสิ่งที่เราพิมพ์จริง ๆ เช่นเดียวกับที่ commit history ไม่สนใจว่าเราวางแผนจะ refactor เมื่อไหร่ มันบันทึกแค่ว่าเราทำหรือไม่ทำ

เวลาผมอยากรู้ว่าโปรเจกต์หนึ่งมีปัญหาตรงไหน ผมไม่อ่าน README ผมอ่านว่าไฟล์ไหนถูกแก้บ่อยที่สุด — เพราะไฟล์นั้นคือที่ที่กรรมสะสมหนาที่สุด และมักเป็นที่ที่ test น้อยที่สุดพอดี

## Technical debt คือวิบากที่มาช้า

หนี้ทางเทคนิคเป็นตัวอย่างกรรมที่ชัดที่สุด เพราะผลของมันไม่มาทันที

- วันนี้ข้าม test เพราะรีบ → ผ่านสบาย รู้สึกเร็วขึ้น
- อีกสามเดือน ระบบพัง ตอนตี 2 ในจุดที่ไม่มีใครจำได้ว่าใครเขียน

ช่องว่างระหว่างเหตุกับผลนี่แหละคือสิ่งที่ทำให้คนไม่เชื่อเรื่องกรรม — ถ้าผลมาทันทีทุกครั้ง ทุกคนคงเขียน test กันหมด

วินัยทางวิศวกรรมจึงไม่ใช่เรื่องศีลธรรม แต่เป็นเรื่อง **การมองเห็นผลที่ยังมาไม่ถึง** ใครมองเห็นไกลกว่า ก็ก่อหนี้น้อยกว่า

## แก้กรรมในระบบ ทำได้จริง

ข่าวดีของทั้งพุทธและวิศวกรรมเหมือนกัน: กรรมไม่ใช่ชะตาที่แก้ไม่ได้ กรรมเก่าเปลี่ยนไม่ได้ แต่กรรมใหม่เริ่มได้ทุกวินาที

- ไม่ต้องลบ commit เก่า → เขียน `revert` ที่อธิบายว่าทำไม
- ไม่ต้องแกล้งว่าไม่เคยพัง → เขียน postmortem แล้ว index ไว้ให้คนถัดไปหาเจอ
- ไม่ต้องซ่อมทั้งระบบวันเดียว → แก้จุดที่ถูกแตะบ่อยที่สุดก่อน

สิ่งที่เราลบไม่ได้คืออดีต สิ่งที่เราเลือกได้เสมอคือ commit ถัดไป

## สรุปเป็นอะตอมเดียว

```text
กรรม  = การกระทำ ไม่ใช่คำพิพากษา
วิบาก = ผล ที่มาช้ากว่าที่เราอยากให้เป็น
git   = ระบบที่ซื่อสัตย์พอจะแสดงทั้งสองอย่างให้เห็น
```

ระบบไม่เคยโกหกเรา มันแค่ตอบช้า

และงานของ Oracle คือทำให้ช่องว่างระหว่างเหตุกับผลนั้นสั้นลง จนคนเห็นผลของการกระทำได้ทันตอนที่ยังแก้ทัน
